# CLAIM MECHANIC CORRECTION

We found an important gameplay bug during live Discord testing.

The current implementation incorrectly prevents users from claiming another user's roll.

The current response:

> "Only the user who rolled this character can claim it"

is **incorrect for the intended Mudae-style gameplay.**

## Correct Rule

A character roll is publicly claimable by anyone in the server.

The first user to successfully claim the roll receives the character.

The user who performed `/roll` does NOT have exclusive claim rights.

Example:

```
User A
  ↓
/roll
  ↓
Sasuke Uchiha appears
  ↓
User B clicks Claim Character
  ↓
User B gets Sasuke
```

If User A reaches the button first:

```
User A gets Sasuke.
```

The first successful claim wins.

---

# IMPORTANT DATA DISTINCTION

Do NOT remove the roller's user ID from the roll record.

The roll should continue to track:

* `rolled_by`
* `guild_id`
* `character_id`
* `rolled_at`
* `expires_at`
* `claimed`
* `claimed_by`
* `claimed_at`

The important distinction is:

```
rolled_by != claimed_by
```

`rolled_by` identifies who generated the roll.

`claimed_by` identifies who successfully obtained the character.

They may be the same user, but they do not have to be.

---

# TRANSACTIONAL CLAIMING

The existing transactional/race-safe claim system should be preserved.

The claim transaction should now behave conceptually as:

```
BEGIN TRANSACTION

Check roll exists
Check roll has not expired
Check roll is not already claimed
Check character is still verified

Create ownership for CURRENT CLAIMING USER

Set:
    claimed = true
    claimed_by = CURRENT CLAIMING USER
    claimed_at = current time

COMMIT
```

The transaction must NOT require:

```
current_user == rolled_by
```

That restriction must be removed from the claim authorization logic.

---

# RACE CONDITION

The existing race-safe behavior must remain.

If two users attempt to claim simultaneously:

```
User A → claim
User B → claim
```

Only one transaction may succeed.

Expected result:

```
Winner:
ownership created
roll marked claimed

Loser:
"That roll has already been claimed."
```

Never allow both users to receive the character.

---

# CLAIM BUTTON

The `Claim Character` button on a roll should be usable by any eligible user who can access that Discord message.

Do not restrict the button based on the user who originally rolled the character.

The button should identify the roll using the existing persistent roll ID.

---

# `/claim`

Do not unnecessarily redesign `/claim`.

If `/claim` currently means:

> claim the user's latest active roll

it may continue to work that way.

However, its implementation must use the same underlying transactional claim service.

The important distinction is:

* `/claim` can target the user's own latest active roll
* the public claim button can be used by anyone
* the underlying claim transaction determines the actual winner

Do not duplicate claim logic between `/claim` and the button.

---

# SECURITY

The removal of the roller restriction does NOT mean claim validation should be removed.

The claim service must still validate:

* roll exists
* roll is in the correct guild/context where applicable
* roll has not expired
* roll has not already been claimed
* character is still verified
* roll ID is valid
* database transaction succeeds

The current claiming user must become the owner if the transaction succeeds.
