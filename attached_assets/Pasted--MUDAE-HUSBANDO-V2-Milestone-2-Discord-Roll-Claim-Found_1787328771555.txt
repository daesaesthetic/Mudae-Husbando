# 6. PERSISTENT ROLL RECORD

Introduce a database-backed roll/session record.

The purpose is to give every Discord roll a unique identity and persistent claim state.

A roll record should contain information equivalent to:

* internal roll ID
* Discord user ID
* Discord guild/server ID
* character ID
* rolled timestamp
* expiration timestamp
* claimed state
* claimed-by user ID if claimed
* claim timestamp if claimed

Use appropriate names/types for the actual schema.

Do not blindly copy this field list if the existing architecture suggests a better design.

The important requirements are:

### Every roll must be uniquely identifiable.

### Every roll must have a claim state.

### The bot must be able to determine whether a roll is still claimable.

### Roll state must survive a bot restart.

# 11. TRANSACTIONAL CLAIMING

This is one of the most important requirements of this milestone.

Claiming must be **atomic and race-safe**.

Consider:

```text
User A clicks Claim
User B clicks Claim
          ↓
     same roll
          ↓
    only one wins
```

It must be impossible for both users to receive the same roll.

The database transaction should perform the necessary checks and writes atomically.

Conceptually:

```text
BEGIN TRANSACTION

Check roll exists
Check roll has not expired
Check roll is not already claimed
Check character is still eligible
Create ownership record
Mark roll as claimed

COMMIT
```

If any check fails:

```text
ROLLBACK
```

Do not perform the ownership insert and roll update as unrelated asynchronous operations.

# 13. DUPLICATES

For this milestone, users should be able to obtain duplicate copies of characters unless the existing game design explicitly prevents it.

Do not accidentally use:

```
UNIQUE(user_id, character_id)
```

if that would prevent future duplicate mechanics.

Prefer a model that can represent:

```
User
  ↓
Character
  ↓
Ownership / acquisition records
```

or another clean design capable of representing multiple copies.

If you choose a quantity-based model instead, make sure the acquisition operation remains transactional.

Document the decision.

# 15. CLAIM OWNERSHIP RULE

A roll belongs to the user who rolled it.

Another user must not be able to steal it by guessing the roll ID or interacting with its button.

The claim system must enforce ownership at the application/database level.

Do not rely only on Discord UI behavior.

---

# 16. BUTTON RESTART BEHAVIOR

The bot may restart after a character has been rolled.

The claim system should still be able to process an existing valid claim button after restart.

Therefore:

* do not store critical claim state only in memory
* do not rely on an in-memory map of roll IDs
* reconstruct all necessary state from SQLite

If Discord button custom IDs need to encode a roll identifier, use that identifier safely.

# 17. EDGE CASES

Return a clear response.

Do not award another copy.

### Expired

Reject the claim.

### Invalid roll ID

Reject safely.

### Wrong user

Reject safely.

### Character no longer verified

Do not award it.

### Database error

Do not partially award the character.

### Duplicate button click

Only the first successful transaction should succeed.

### Bot restart

Persistent rolls and ownership should remain consistent.

### Missing image

Display the card without an image or with a safe fallback.

### Missing description

Use a neutral fallback.

Never invent information to fill missing fields.
