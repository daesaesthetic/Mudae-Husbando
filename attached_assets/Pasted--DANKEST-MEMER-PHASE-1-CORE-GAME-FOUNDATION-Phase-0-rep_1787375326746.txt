# DANKEST MEMER — PHASE 1
## CORE GAME FOUNDATION

Phase 0 repository audit is complete.

The current project is a functional character-collection game foundation with:

- PostgreSQL persistence
- verified character catalog
- /roll
- /claim
- character collections
- profiles
- search
- wishlists
- favorites
- transactional character claiming

The long-term goal is to expand this project into "Dankest Memer": a broad Discord economy/game bot inspired by the gameplay systems of Dank Memer.

DO NOT remove or rewrite the existing character-collection functionality.

This phase establishes the shared foundation required for future economy and gameplay systems.

IMPORTANT:

Do not implement beg, work, crime, rob, gambling, fishing, hunting, pets, farming, quests, trading, or other large gameplay features yet.

Do not add large user-facing feature sets.

Focus on reusable infrastructure.

---

# 1. DATABASE MIGRATION FOUNDATION

The current game database uses direct PostgreSQL SQL with ad-hoc startup schema creation.

Replace the ad-hoc schema evolution approach with a lightweight, versioned migration system.

Requirements:

- Existing PostgreSQL data must be preserved.
- Existing tables must not be unnecessarily recreated.
- Existing character data must remain intact.
- Existing users, collections, rolls, wishlists, and favorites must remain intact.
- Migrations must run in deterministic order.
- Applied migrations must be recorded.
- Already-applied migrations must not run again.
- Future migrations must be easy to add.
- Startup must fail safely if a migration fails.

Do not introduce a large ORM rewrite.

Do not migrate from PostgreSQL to another database.

The existing direct PostgreSQL approach may remain if it is currently appropriate.

---

# 2. CENTRAL GAME ECONOMY SERVICE

Create a reusable economy abstraction.

The existing `mudae_users.currency` field may be retained, but currency mutations must no longer be implemented ad hoc in future commands.

Create a centralized service capable of operations conceptually equivalent to:

- getBalance
- addCurrency
- removeCurrency
- transferCurrency
- canAfford

Requirements:

- Never allow negative balances unless explicitly supported by a future system.
- Use PostgreSQL transactions for mutations.
- Use atomic SQL operations for balance changes.
- Prevent concurrent requests from creating or destroying currency incorrectly.
- Validate amounts.
- Reject NaN, Infinity, zero/negative values where inappropriate, and unsafe numeric inputs.
- Return structured success/failure results.
- Do not expose raw database errors to Discord users.

Do not add economy commands yet.

---

# 3. ECONOMY TRANSACTION RECORDS

Create a persistent transaction/audit model for currency changes.

Each transaction should be capable of recording:

- unique transaction ID
- user ID
- amount
- transaction type/reason
- optional related user
- timestamp
- optional metadata

The purpose is to make future economy operations auditable.

Do not log sensitive information unnecessarily.

Do not retrofit historical transactions that never existed.

---

# 4. CENTRALIZED COOLDOWN SERVICE

Create a reusable cooldown system for future gameplay commands.

It must support:

- command/action identifier
- user scope
- optional guild scope
- duration
- remaining-time calculation
- setting a cooldown
- checking a cooldown
- clearing a cooldown

Design it so future commands can simply request:

"Is this action available?"

without implementing their own cooldown logic.

Cooldown state should persist across bot restarts.

Use PostgreSQL rather than an in-memory-only map.

Prevent obvious concurrent bypasses.

Do not add cooldowns to existing `/roll` yet unless required for infrastructure testing.

---

# 5. RANDOMNESS / REWARD FOUNDATION

Create a small reusable game RNG/reward utility.

It should support future systems such as:

- reward tables
- deterministic testing where practical

Do not change the existing character roll probabilities yet.

Do not introduce random reward systems that aren't currently needed.

The purpose is to prevent every future command from implementing its own RNG logic.
