OBJECTIVE

Implement a persistent roll-pool and replenishment system for /roll, replacing the current per-roll cooldown behavior.

The intended gameplay model is similar to Mudae's Waifu-style roll availability:

Normal User
───────────

5 available rolls

/roll
→ 4 remaining

/roll
→ 3 remaining

/roll
→ 2 remaining

/roll
→ 1 remaining

/roll
→ 0 remaining

WAIT FOR REPLENISHMENT

↓
5 rolls available again

The user must be able to consume their available rolls consecutively without waiting between individual rolls.

A replenishment cooldown begins only after the pool reaches zero.

3. REPLACE PER-ROLL COOLDOWN BEHAVIOR

The current system uses a cooldown that prevents a user from immediately rolling again.

That behavior must be replaced for normal users.

The desired behavior is:

/roll
↓
success
↓
/roll immediately
↓
success

provided the user still has available rolls.

There must be no cooldown between individual rolls.

The cooldown applies only after the user has exhausted the entire pool.

7. NORMAL ROLL CONSUMPTION

Each successful normal /roll consumes exactly one available roll.

Example:

5
↓
/roll
↓
4

Then:

4
↓
/roll
↓
3

Continue until zero.

The roll operation must remain transactional.

At minimum, the successful operation must ensure that:

Availability is checked atomically.
One roll is consumed.
The lifetime roll statistic is incremented.
The persistent roll record is created.
The selected character still comes from the existing verified-character roll system.

Do not create a roll record if the user did not successfully consume a roll.

8. ATOMIC CONSUMPTION

Concurrent requests must be safe.

If the user has:

available_rolls = 1

and two /roll requests happen simultaneously:

Request A ─┐
           ├── same user
Request B ─┘

the result must be:

Exactly one succeeds.
Exactly one is rejected.
available_rolls never becomes negative.

Use the existing PostgreSQL transaction/locking patterns.

Do not solve this with an in-memory lock.

The database must remain authoritative.

9. EXHAUSTION

When:

available_rolls = 0

normal /roll must stop succeeding.

The response should clearly communicate that the user's rolls are exhausted and that replenishment is pending.

Do not continue using the old misleading per-roll cooldown message:

You can roll again after the current roll cooldown expires.

The user has not merely triggered a cooldown after one roll.

They have exhausted their current pool.

Use the existing Discord presentation conventions.
