# Mudae Husbando V2 — Claim Availability Follow-Up

## PURPOSE

Continue from the current repository state and the previous Roll Pool Adjustment task.

The previous investigation correctly determined:

> The repository has no existing claim-cooldown duration or persistent claim-availability mechanism to restore.

Therefore, do **not** search for an existing claim cooldown to restore.

We are explicitly establishing the intended gameplay rule now.

---

# 1. NEW CLAIM AVAILABILITY RULE

Implement a persistent **claim availability pool** separate from the roll pool.

Normal users receive:

```text
1 available claim
```

The default claim replenishment duration is:

```text
1 hour
```

After the user successfully claims a character:

```text
available_claims = 0
claim_replenishment_at = current time + 1 hour
```

The user cannot successfully claim another character while the claim is unavailable.

When the replenishment timestamp expires:

```text
available_claims = 1
claim_replenishment_at = NULL
```

The next claim is allowed.

Add persistent state to the authoritative user record using an additive PostgreSQL migration.

Conceptual fields:

```text

claim_replenishment_at
```

Use the repository's actual naming and SQL conventions.

Expected conceptual schema:

```text
available_claims INTEGER NOT NULL DEFAULT 1
claim_replenishment_at TIMESTAMPTZ
```

Add an appropriate non-negative constraint if consistent with the existing roll-pool implementation.

Do not modify historical migrations.

Do not recreate the user table.

Do not reset existing users.

Existing users should receive:

```text
available_claims = 1
claim_replenishment_at = NULL
```

Existing gameplay data must remain untouched.

* collections

`claims_count` remains a lifetime statistic.

---

# 4. CLAIM TRANSACTION

Integrate claim availability into the existing `claimRoll()` transaction.

This is critical.

The existing claim transaction and global character uniqueness system are already authoritative.

Preserve:

* PostgreSQL transaction
* roll row locking
* character advisory locking
* ownership checks
* expiration checks
* verified-character checks
* first-claim-wins behavior
* collection insertion
* claim count increment

The new claim availability state must be integrated without weakening any of these protections.

A successful claim must atomically:

1. Lock the user's database row appropriately.
2. Restore an expired claim pool if applicable.
3. Verify claim availability.
4. Perform all existing claim validation.
5. Claim the character.
6. Update the collection.
7. Increment `claims_count`.
8. Consume exactly one available claim.
9. If the claim reaches zero, start the replenishment timestamp.
10. Commit.

If the claim fails for any reason, the user must **not lose their claim availability**.

Do not consume the claim before the existing claim transaction has successfully completed.

---

# 5. CONCURRENCY

The database must remain authoritative.

Do not use an in-memory lock.

If:

```text
available_claims = 1
```

and two claim requests from the same user happen concurrently:

```text
Request A ─┐
           ├── same user
Request B ─┘
```

the result must be:

```text
Exactly one successful claim.
Exactly one rejected claim.
available_claims never becomes negative.
```

Use the existing PostgreSQL transaction/locking architecture.

The user row should be protected so concurrent claims cannot both consume the same claim availability.

The existing character-specific advisory lock and global uniqueness protection must remain intact.

---

# 6. CLAIM REJECTION

After the user successfully claims:

```text
available_claims = 0
claim_replenishment_at = future timestamp
```

A subsequent immediate `/claim` must be rejected.

The response should clearly communicate that the user's claim is unavailable and that another claim will become available after the replenishment period.

Do not report:

> This roll has already been claimed.

unless the actual roll being targeted is independently already claimed.

The user-level claim availability restriction is a separate reason for rejection.

Use the existing Discord presentation conventions.

---

# 7. CLAIM AVAILABILITY IS INDEPENDENT FROM ROLLS

This is mandatory.

The roll pool and claim pool are separate systems.

Example:

```text
10 rolls
1 claim

/roll
→ 9 rolls
1 claim

/claim
→ 9 rolls
0 claims

/roll
→ 8 rolls
0 claims
```

The user must still be able to roll while their claim is unavailable.

Likewise, rolling must never restore or consume a claim.

Do not connect:

```text
available_rolls
```

and:

```text
available_claims
```

except through the shared user record.

---

# 8. CLAIM REPLENISHMENT

Replenishment should use the same persistent/lazy model established for rolls.

Do not use:

```text
setTimeout()
setInterval()
```

as the source of truth.

The database timestamp is authoritative.

If:

```text
available_claims = 0
claim_replenishment_at = future
```

the claim remains unavailable.

If:

```text
available_claims = 0
claim_replenishment_at = expired
```

the next relevant claim interaction should atomically restore the pool.

After restoration:

```text
available_claims = 1
claim_replenishment_at = NULL
```

Then the claim may proceed.

Do not require a continuously running background timer.

---

# 9. FAILED CLAIMS MUST NOT CONSUME AVAILABILITY

This is particularly important because the existing claim system performs several validations.

If a claim fails because of:

* already claimed roll
* expired roll
* character ownership conflict
* invalid roll
* unverified character
* transaction failure
* any other existing claim validation

then:

```text
available_claims
```

must remain unchanged.

Only a **successful character claim** consumes the user's claim availability.

---

# 10. EXISTING GLOBAL UNIQUENESS MUST REMAIN UNCHANGED

Do not solve this problem by modifying character ownership.

The existing rule remains:

> There is only one globally claimable copy of each character. The first successful claimant owns it.

Preserve all existing advisory locking and ownership checks.

The new claim pool controls:

```text
Can this user perform another claim?
```

It does not control:

```text
Who owns this character?
```

These are separate concerns.

---
